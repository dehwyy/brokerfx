# Changelog

## v0.8.0

- batch: `Opts.MinBatch` / `BROKERFX_BATCH_MIN` and `Opts.LingerMax` / `BROKERFX_BATCH_LINGER_MAX` (off): after the first linger fetch the consumer keeps fetching until `MinBatch`, a full batch or `LingerMax`. `MinBatch > Max` and `LingerMax >= AckWait/4` fail `New`; `MinBatch` without `LingerMax` is off with a warning. (ARCH-04)
- batch: `Opts.Replicas` / `BROKERFX_BATCH_REPLICAS` (0 = `Pipeline × Max` as before). With `Replicas > 0` an unset `MaxAckPending` becomes `batch.MaxAckPendingFor(replicas, pipeline, max)` = `ceil(1.5 × R × P × M)`; an explicit lower value fails with `ErrMaxAckPending`; a durable left by an older pod is accepted. Logged at start. (ARCH-17, ERR-52, ERR-08)
- batch: `InTxOpts.ApplyResults` with per-message verdicts and `batch.Skip()`; non-acked messages release their `processed_messages` claim in the same transaction. `batch.Observer` (`OnFetch`, `OnApply`, `OnBisect`, `OnSettle`) on `Opts` and `InTxOpts`. (ARCH-09)
- batch: `InTxOpts.OrderKey` bisects by key groups; a failed group commits its longest good prefix and holds the tail with `NakDelay(…, ErrOrderBlocked)`, which does not count toward `OnPoison`; an ack after a non-ack of the same key rolls the attempt back. (MQ-16, ERR-48)
- outbox: `Config.TxDrain` / `BROKERFX_OUTBOX_TX_DRAIN` (off) and `TxDrainPublishTimeout` / `BROKERFX_OUTBOX_TX_DRAIN_PUBLISH_TIMEOUT` (2s, below 25s): claim, publish and write-back of failed rows in one transaction, no `IN_FLIGHT`. Unknown outcome keeps `attempts`, a refusal counts an attempt and parks at `MaxAttempts`. Off for the process after 3 transaction failures in a row; in `DeleteAfterSend` needs no extra `NOT NULL` columns without default. `UpdateAfterSend` marks rows `DONE` in the transaction instead of deleting them. (DB-04)
- outbox: id lists as `= ANY(?::uuid[])` / `= ANY(?::text[])` by the detected type of `outbox_events.id`, the batch claim of `processed_messages` through `unnest … WITH ORDINALITY`; `IN ?` stays when the type is unknown. No flag. (DB-23)
- outbox: `Config.PendingGaugeInterval` / `BROKERFX_OUTBOX_PENDING_GAUGE_INTERVAL` (0 = off) feeds `PendingObserver.OnPending` with the `PENDING` count capped at 10 000 and the oldest age by the database clock. (ERR-25)
- outbox: `Config.CleanupBatch` / `BROKERFX_OUTBOX_CLEANUP_BATCH` (0 = one `DELETE` as before): `DONE` and expired `PARKED` rows deleted in `ctid` batches with a 100ms pause, off the relay loop. (ERR-53)
- outbox: `Config.LatestOnlyPrefixes` / `BROKERFX_OUTBOX_LATEST_ONLY_PREFIXES` (`$KV.` always): one publish per subject in a batch, highest `Brokerfx-Latest-Version` when every row has it, else the last row; `SupersededObserver.OnSuperseded(n)`. (MQ-08)
- outbox: optional `Message.Headers` per element in `SaveMessages` and `SaveMessage`; the element wins over `WithHeaders`, reserved headers are checked per element. (SVC-02)
- producer: `ProduceSync(ctx, event, opts...)` waits for the PubAck within `ctx` and returns the publish error. (ERR-43)
- jetstream: `BROKERFX_JS_PUBLISH_ASYNC_MAX_PENDING` sets the async publish window (unset = nats.go default). (ERR-83)
- pgtimer: new package. Lease-claim poller over a timer table the service owns (`New`, `Handle`, `Start`, `Stop`, `RegisterLifecycle`, `Observer`), delete after the handler by key, name, attempt and the exact lease `due_at`; env `BROKERFX_PGTIMER_LEASE` (60s), `_HANDLER_TIMEOUT` (30s), `_POLL` (1s), `_BATCH` (100), `_CONCURRENCY` (8). (MQ-02)
- timedactor: `Hold` keeps the later of the original deadline and `now + MaxHoldDuration`; before, a timer due in 10 minutes was moved to 15 seconds. (ERR-39) README documents the at-most-once callback of timedactor. (ERR-70)
- With the new fields and env unset, behaviour is the same as in v0.7.0 except the `Hold` deadline fix and the `= ANY` id lists.

## v0.7.0

- timedactor: `Config.MarkerTTL` (0 = off, at least 1s). Fired and cleared keys are removed with `Purge(PurgeTTL(MarkerTTL))` under the same revision guard, and the bucket gets `LimitMarkerTTL`, so delete markers expire after `MarkerTTL` instead of living for `BucketTTL`. With `MarkerTTL = 0` an existing bucket keeps its marker TTL. Rollback trap: once enabled, an image below v0.7.0 crash-loops with `message TTL status can not be disabled`; delete the bucket before rolling back and let the service reconciler restore the timers (mandatory).
- timedactor: `Config.RescanInterval` (0 = rescan every `CheckInterval` as before). `> 0` sets the rescan period, adds a rescan right after the initial watch values, and retries an unexpected key removal error locally after `CheckInterval` instead of skipping the callback until the next rescan.
- consumer: `Opts.MaxInFlight` / `BROKERFX_CONSUMER_MAX_IN_FLIGHT` (0 = one goroutine per message as before). `K > 0` bounds running handlers to `K`, pulls one message per request (no message sits in the nats.go buffer without a heartbeat), blocks the receive callback while all slots are busy, heartbeats a waiting message from receipt and uses a heartbeat of `min(5s, AckWait/3)`. `Drainer.DrainContext(ctx)` waits within `ctx` until all `K` slots are free (a handler that took a slot while the subscription was closing included); a message still waiting for a slot then gets `Nak` instead of a handler; `Drain()` does the same without a deadline.
- consumer: `Opts.NakBackoff` / `BROKERFX_CONSUMER_NAK_BACKOFF` (off by default; `true` = `consumer.DefaultNakDelays` 1s/5s/30s/2m/5m, or a list such as `1s,2s,5s`). All three NAKs (handler error, before-middleware error, panic) become `NakWithDelay` by `NumDelivered`. Without `MaxDeliver` a failing message is redelivered forever. `batch.DefaultDelays` is now the same slice as `consumer.DefaultNakDelays`. Invalid explicit opts return `consumer.ErrInvalidOpts`; invalid env logs a warning and keeps the default.
- consumer-opts-builder: `WithReplicas(n)` (0 = inherit) and `FitReplicas(cfg, streamCfg)`, applied by `consumer.New` and `batch.New`: a count the server would reject (not the stream's on workqueue/interest, above the stream's on limits) is reset to 0 with a warning. `(*stream.Stream).Config()` returns the cached stream config.
- stream-opts-builder: `RoleCommand` and `RoleReply` default to no compression, event/result/DLQ keep S2; `WithCompression` wins in either call order; `CompressionFor(role)` for raw configs. Existing command/reply streams switch to none on the next start (new blocks only).
- stream: `Duplicates` is clamped to `MaxAge` when `MaxAge > 0` and the window is longer, in `Build()`, `stream.CreateOrUpdate` and `kv.Ensure` (bucket TTL), with a warning (`FitDuplicates`) that names the largest outbox `StallThreshold` the clamped window still covers (`MaxAge / 2`, the `Duplicates >= 2 × StallThreshold` invariant). Valid configs are unchanged; a config the server used to reject now starts, so check the invariant on short-lived streams.
- outbox: event ids are UUIDv7 by default (`BROKERFX_OUTBOX_ID_V7=false` for UUIDv4, read once per process); string format, `Nats-Msg-Id` and `processed_messages` are unchanged. `OutboxEvent` no longer declares the `state` and `created_at` indexes, so `AutoMigrate` does not create `idx_outbox_events_state` / `idx_outbox_events_created_at` on a clean database; existing indexes are not dropped.
- Logs: `outbox batch processed` and the two `hold released` lines of timedactor moved from info to debug.
- `github.com/samber/lo` is no longer a dependency.
- With the new fields and env unset, behaviour is the same as in v0.6.2 except the command/reply compression default, the duplicates clamp, UUIDv7 ids and the log levels.

## v0.6.2

- Outbox claim v2 runs in an explicit transaction. Before, the claim `UPDATE` could finish and `ClaimTimeout` expire right after it: the statement was already committed, the rows stayed `IN_FLIGHT` with no receiver until `StallThreshold` (5m), and were then published with an expired signature. Now the claim is committed only when the rows were read and the claim context is still alive; otherwise the transaction rolls back and the rows stay `PENDING`.
- Env `BROKERFX_OUTBOX_CLAIM_TIMEOUT`, `BROKERFX_OUTBOX_STALL_THRESHOLD`, `BROKERFX_OUTBOX_STALL_RECLAIM_INTERVAL` (`time.ParseDuration`, must be positive). An invalid value is ignored with a warning; a valid value wins over `Config`.
- `signature.NewKeyedResigner(keys map[string]ed25519.PrivateKey)`: an `outbox.Signer` that refreshes the signature at publish time for messages signed with one of its keys. Messages signed with another key or not signed at all pass through unchanged.
- With the new env unset and no `Signer` configured the behaviour is the same as in v0.6.1.

## v0.6.1

- `outbox.EnsurePendingIndex`: `pg_try_advisory_lock` instead of a blocking `pg_advisory_lock`; when another instance holds the lock the call returns `nil` at once. In v0.6.0 a second instance waited for the lock inside `SELECT pg_advisory_lock` with a snapshot, `CREATE INDEX CONCURRENTLY` waited for that snapshot, and Postgres reported a deadlock, leaving the index invalid. The build now runs with `statement_timeout = 0` on its connection and restores the previous value afterwards.

## v0.6.0

- Outbox claim v2 behind `Config.ClaimV2` or env `BROKERFX_OUTBOX_CLAIM_V2=true|1` (off by default). One statement `WITH c AS MATERIALIZED (SELECT id ... WHERE state <> 'DONE' AND state = 'PENDING' AND (next_attempt_at IS NULL OR next_attempt_at <= now) ORDER BY created_at LIMIT n FOR UPDATE SKIP LOCKED) UPDATE ... FROM c ... RETURNING`: literal states, no `OR` with stalled rows, so the partial index `idx_outbox_events_pending_created_at` is used and the plan no longer falls into a Nested Loop Semi Join on empty statistics. Stalled `IN_FLIGHT` rows go back to `PENDING` in a separate statement at most once per `StallReclaimInterval` (default 1m, not above `StallThreshold`). Each claim/reclaim has a `ClaimTimeout` (default 5s). Applies to the batched and the plain relay on the v2 schema; the published set and order are the same as with the flag off.
- `outbox.EnsurePendingIndex(ctx, db)`: `CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_outbox_events_pending_created_at ON outbox_events (created_at) WHERE state <> 'DONE'` under an advisory lock, rebuilds an invalid index, no-op without `outbox_events`. Not part of `AutoMigrate`.
- `(*OutboxStore).SaveMessages(ctx, messages, opts...)`: multi-row `INSERT` (chunks of 500) in the caller's transaction, input order kept through client-assigned `created_at` (+1 µs per message), all validation before the write.
- Existing behaviour unchanged with the flag off: `Save`, `SaveMessage`, `AutoMigrate`, `DefaultConfig()`, `RecommendedConfig()` and the old claim are as in v0.5.1.

## v0.5.1

- `batch.InTx`: when the transient retry budget is spent the remaining messages get `Nak(err)` instead of `NakDelay(1s)`. Before, every attempt was retried after 1 s and still counted toward `MaxAttempts`, so a Postgres outage or failover longer than about 6 s sent every message of that window to `OnPoison` (DLQ). Now the retry ladder of `Opts.Delays` applies (1s/5s/30s/2m/5m by default, about 8.5 minutes before `OnPoison`). `InTxOpts.TransientDelay` no longer has a default; a positive value is an explicit override of the ladder delay.

## v0.5.0

- New package `pkg/nats/jetstream/consumer/batch`: a pull consumer that gives the handler a batch (`Handler func(ctx, []jetstream.Msg) []batch.Result`) and applies a verdict per message (`Ack`, `Nak`, `NakDelay`, `Term`) after the handler returns. Fetch loop with `Max` / `Linger` / `Pipeline`, one `InProgress` heartbeat per batch every `AckWait/2`, panic isolation (unsettled messages are re-run one by one), `Drain(ctx)` that naks fetched-but-not-started messages and waits for batches in progress, `OnFatal` once when the consumer is deleted. Survives a NATS server restart.
- Retry policy of the service `deadletter` packages built in: Nak delays by `NumDelivered` from `Opts.Delays` (`batch.DefaultDelays` 1s/5s/30s/2m/5m), the library counts attempts (`Opts.MaxAttempts`, default `len(Delays)+1`, `-1` unlimited) and then calls `OnPoison`; `batch.Poison(err)` goes to `OnPoison` on the first delivery. If `OnPoison` fails the message is `NakWithDelay`ed, not terminated, and goes to `OnPoison` again on redelivery. `New` rejects a consumer whose server `MaxDeliver` is not `-1` and not above `MaxAttempts` (`ErrMaxDeliver`).
- `batch.InTx`: one transaction per batch, batch dedup through one `INSERT ... ON CONFLICT DO NOTHING RETURNING` into `processed_messages`, bisection down to the failing message on a non-transient error, a shared transient retry budget, `NoDedup` for projections with a version guard, `batch.DefaultTransient` (SQLSTATE serialization/deadlock/lock/cancel/shutdown, classes 08 and 53, bad conn, deadlines, net timeouts).
- `batch.CoalesceByKey` and `batch.GroupByKey`: one result per key group, applied to every message of the group.
- `batch.New` reuses an existing durable without moving its start position (deliver policy and start sequence are kept, other fields are updated). `batch.ResumeSequence(ctx, js, stream, oldDurable)` returns the old durable's ack floor + 1 (0 when it does not exist) for the switch to a new batch durable.
- `ConsumerOptsBuilder.WithMaxAckPending` and `WithDeliverByStartSequence` (0 keeps `DeliverAll`). The batch consumer sets `MaxAckPending = Pipeline × Max` when it is not set and rejects a lower explicit value (`ErrMaxAckPending`).
- New package `pkg/nats/jetstream/consumer/cleanup`: background deletion of `processed_messages` older than `Retention` (default 48h) in batches, `cleanup.Module` for fx, `cleanup.EnsureIndex` for the `processed_at` index.
- Outbox batched relay R1 behind `Config.Batched` (or `BROKERFX_OUTBOX_RELAY_BATCHED`): one-statement claim with `FOR UPDATE SKIP LOCKED ... RETURNING`, `Linger` after a wakeup (default 5ms when batched), repeat while batches are full, `outbox.BatchProducer` / `(*JetStreamProducer).ProduceBatch` publish the batch with one ack timer, successes deleted or marked DONE with one statement. Only on the v2 schema; the legacy schema keeps the old branch.
- Env: `BROKERFX_BATCH_MAX` (16, 1..256), `BROKERFX_BATCH_LINGER` (5ms, up to 1s), `BROKERFX_BATCH_PIPELINE` (1, 1..8), `BROKERFX_PROCESSED_RETENTION` (48h), `BROKERFX_PROCESSED_CLEANUP_INTERVAL` (1h), `BROKERFX_OUTBOX_RELAY_BATCHED` (off).
- Existing behaviour unchanged: `consumer.New`, `consumer.Opts`, `WithIdempotency`, `AutoMigrateProcessed`, `outbox.DefaultConfig()` and `outbox.RecommendedConfig()` work as in v0.4.6; the new `outbox.Config` fields are off at their zero value.
- Rollout note: services opt in per consumer (new `*-batch` durable started at `ResumeSequence` of the old one, behind a service flag) and per relay (`BROKERFX_OUTBOX_RELAY_BATCHED`). With R1 use `ModeDeleteAfterSend` and the partial index `idx_outbox_events_pending_created_at ON outbox_events (created_at) WHERE state <> 'DONE'`. Add `cleanup.Module` wherever `processed_messages` is written.

## v0.4.5

- `timedactor.Config` gets `FileStorage` (bucket in file storage, default stays memory) and `Replicas` (0 resolves `NATS_JS_REPLICAS_KV` / `NATS_JS_REPLICAS`, malformed env fails `New`). Needed to move the `processing-timers` KV to file R3.

## v0.4.3

- Outbox schema caps are no longer pinned when legacy. `OutboxRelay` and `OutboxStore` re-detect the schema (every 5 s, throttled) until `headers`, `attempts`, `last_error`, `next_attempt_at` and `outbox_retries` all exist, and cache only a complete schema. Before, a relay or store that detected the schema before `outbox.AutoMigrate` ran stayed on the legacy branch for the whole process life: rows with `Paylonium-Envelope` headers were published without them (and the store rejected header writes with `ErrSchemaOutdated`) until a restart. The relay logs a warning at start when the schema is incomplete.
- Stream and KV replicas from env (NF-D-276). `NATS_JS_REPLICAS` (1..5, default 1) is the global value, `NATS_JS_REPLICAS_<EVENT|COMMAND|RESULT|REPLY|DLQ|KV>` overrides it per role. `StreamOptsBuilder` applies the role value (`WithRole`) unless `WithReplicas` is called explicitly (explicit wins in either order). `stream.CreateOrUpdate` with `cfg.Replicas < 1` resolves the event scope. `kv.Ensure` with `Replicas == 0` resolves the KV scope; `Replicas < 0` is still `ErrReplicasRequired`, an explicit `Replicas >= 1` wins over env. Create and update of an existing stream both apply the value, so a restart on an R3 cluster does not return R1. A malformed value fails startup (`ErrInvalidReplicasEnv`, `StreamOptsBuilder.Err()`). Services must stop hard-coding `WithReplicas(1)` / `kv.Opts{Replicas: 1}` for the env to take effect.
- Connection resilience in `pkg/nats/conn`: `MaxReconnects` 0 or negative means unlimited (-1), `ReconnectWait` defaults to 2 s with 500 ms jitter, `RetryOnFailedConnect` is always on. New `Opts.Shutdowner fx.Shutdowner` calls `Shutdown(ExitCode(1))` when the connection is closed for good (not on a deliberate `Close`/`Drain`), `Opts.OnClosed` is an extra hook. Disconnect, reconnect and close are logged.
- `consumer.Opts.OnFatal` is called when the pull subscription ends for good (`ErrConsumerDeleted` / `ErrConsumerNotFound`); consume errors are logged. Pull consumers keep running through a server restart (covered by an embedded nats-server test).
- `timedactor.Subscribe` reopens its KV watcher with backoff when `Watch` fails or the updates channel closes, instead of silently ending the goroutine (and its safety-net rescan).

## v0.4.1

- Stream default `MaxBytes` lowered from 2 GiB to 256 MiB. 48 streams at 2 GiB reserve 96 GiB of JetStream storage against well under 1 MiB of real data.
- Separate limits per explicit stream role (NF-D-192): `StreamOptsBuilder.WithRole(Role)` with `RoleEvent` (default, 256 MiB, `DiscardOld`) and `RoleCommand`, `RoleResult`, `RoleReply` (1 GiB) and `RoleDLQ` (256 MiB), all `DiscardNew` (overflow is a publish error, the outbox retries). `WithDiscard` sets the policy explicitly. `LimitsFor(role)` returns the same numbers for raw `jetstream.StreamConfig` users. A stream that never calls `WithRole` is an event stream, so services must opt in when they bump.
- `BROKERFX_STREAM_MAX_BYTES` overrides the event limit and `BROKERFX_STREAM_MAX_BYTES_CRITICAL` the command/result/reply limit, `BROKERFX_STREAM_MAX_BYTES_DLQ` the DLQ limit (positive integers, bytes). An explicit `WithMaxBytes` takes priority over both. A malformed or non-positive value fails startup: `StreamOptsBuilder.Err()`, `stream.New` returns `ErrInvalidMaxBytesEnv`, `Build()` panics.
- `stream.New` no longer lowers `max_bytes` of an existing stream when its `State.Bytes` exceeds half of the requested limit. The current limit is kept and a warning is logged. Lowering below that threshold and raising the limit behave as before.
- New exported helpers for services that create streams from raw `jetstream.StreamConfig`: `stream.CreateOrUpdate(ctx, js, cfg)` applies the same shrink guard, `streamoptsbuilder.MaxBytesFromEnv()` returns the env-or-default limit.
- KV buckets (`kv.Ensure`) are unchanged.
- Rollout note: services pick up the new default at the next start after bumping brokerfx. Existing streams are updated by `CreateOrUpdateStream` when the owner restarts.
